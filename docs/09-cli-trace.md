# Step 9 — 一次 Run 要能回答：干了什么、为什么停、花了多少

前面八步把「一次 Run 如何发生、如何活下来、如何被替换」建完了，但**没人能用它**：
`runtime.run(task)` 是一个只有测试能调用的生成器，读完一次 Run 需要自己写一段脚本。
这一步加的是产品面，它要回答的唯一问题是：

> 一个人怎么发起一次 Run，又怎么看懂它。

这个问题的答案有三块，而它们各自都是前面某一步的**纯投影**，不是新的真相：

```text
kuse run     发起 + 回放式的收尾     ── Runtime 的接线（步 4/5/6/7）+ 适配器（步 8）
kuse trace   看懂一次已有 Run        ── traceOf(日志)            ← 本步新增
kuse runs    这个会话有哪几次 Run     ── SessionStore            （步 7）

── 证据核对 ──────────────────────────────────────────────────────────────
auditRun(日志, 工具)                  ← 本步新增，把 README 那句承诺变成可执行的
```

```bash
kuse run "这个仓库里哪些地方在用 assertSafePathSegment？" --repo . --offline

── 调用了什么 ─────────────────────────────────────────────────────────────
   1  list_dir({"path":"."})  ok  4ms
   2  search_text({"pattern":"assertSafePathSegment","maxMatches":5})  ok  37ms
   3  read_file({"path":"src/store/run-log-jsonl.ts","startLine":1,"endLine":40})  ok  1ms

── 为什么停 ──────────────────────────────────────────────────────────────
  completed（有结论，材料齐）

── 证据核对 ──────────────────────────────────────────────────────────────
  证据 4/4 条对得上材料
  论断 0 条明说没有依据
```

## 一、同一份日志的三种看法

一份事件日志到今天已经回答三个不同的问题，而它们各自需要一个消费者：

| 问题 | 消费者 | 形状 |
|---|---|---|
| 那串事件说的是哪个**状态**？ | `replayAgentState`（步 7） | `AgentState` |
| 那次 Run 停在**哪儿**？ | `runStatusOf`（步 7） | `RunStatus` |
| 它**干了什么、为什么停、花了多少**？ | `traceOf`（本步） | `RunTrace` |

三者都是纯函数，都不碰磁盘、不看时钟、不问端口——**日志是唯一真相，而它们是同一份真相的三种看法**。

第三种与前两种有一处**刻意的差别**：回放对 `human_input_received` / `run_resumed` 抛错
（它要重建状态，而"人的回答怎么进 transcript"还没有定论），trace **不抛**——它不重建状态，
只读事实。"这个 Run 收过一个人的回答、然后接着跑了"是一个可以陈述的事实，哪怕我们还不知道
它把状态推进到了哪里。

这不是对回放的宽容，而是两个问题各自的严格程度不同：**状态的每一格都必须有依据，
而"发生了什么"只要是日志里写着的事就能说。**

trace 与 CLI 都只看得见"已经发生完的一次 Run"。有几件**只有跑起来才看得到**的事
——中途换掉模型、取消落在决策与工具调用**之间**、一次挂起的 Run 在"崩溃"之后从磁盘被认出来
——它们不在这个文档的正文里，而在一个可以自己跑的走查脚本里：

```bash
node examples/end-to-end.mjs
```

## 二、退出码就是「为什么停」的机器可读形式

```text
 0  complete        有结论，材料齐
10  partial         有结论，但缺材料（`missingMaterial` 里有名字）
11  failed          失败（码在 `run_failed` 事件里）
12  cancelled       被取消
13  awaiting_human  挂起等人（**不是失败**：它在等一个只有人能给的输入）
 2  用法错误        参数 / 模型 / 会话不对——**Run 没有开始**
 3  内部错误        日志坏了之类：连"发生了什么"都答不出来
```

10~13 与 2/3 分开是有意的：前者是"Run 发生了但没走完"，后者是"Run 根本没发生"。
把它们混成一个非零码，脚本就分不清**"重试有用"**与**"重试之前得先改参数"**。

这个映射只有一处（`main.ts` 的 `exitCodeFor`），而且用 `never` 钉住了穷尽性：
`TraceStop` 多一种收场，那个 `switch` 立刻编译不过。

## 三、证据核对：它核对的不是「对不对」

README 把真实任务写成一句话：Agent 有用的判据是**每条论断都指向证据**，而找不到依据时
它明说缺了什么。前半句到步 8 为止只被**要求**过（system prompt 让模型这么做）、
从来没有被**核对**过——模型完全可以在 `evidence` 里写一个它从没读过的路径，而没有任何东西会响。

这里落地的核对不是"这句话在语义上对不对"（那需要另一个模型，是另一个循环），而是便宜得多、
而且**可以完全确定**的一件事：**这些行，我们真的看到过吗？**

两者不能混为一谈。一个模型可以引用真实存在的行却得出错误结论（推理问题），也可以得出
正确结论却引用了没读过的行（**证据问题**）。后者更危险：它让结论看起来有依据，而依据是编的。

一个真实的核对结果是这样：

```text
── 证据核对 ──────────────────────────────────────────────────────────────
  证据 2/2 条对得上材料
  论断 0 条明说没有依据

  证据 0/0 条对得上材料（这条结论引用零条证据）     ← 或
  ✗ src/ghost.ts:5-5 —— 没有任何一次调用看到过这几行
  · 无依据：没有成功读到任何文件的内容。
```

## 四、脱敏有两个方向，而它们看起来是矛盾的

这是本步里最容易做错的一件事。必须把两类"秘密"分开，因为它们的正确处理方式**相反**：

| | 例子 | 从哪来 | 怎么办 |
|---|---|---|---|
| **我们自己的凭据** | provider 的 API key | 进程环境 | **落盘之前就抹掉** |
| **被分析仓库里的秘密** | 仓库某行里写死的 key | 材料本身 | **保留原样**，因为那正是要报告的东西 |

第二类不能改写，理由是本项目的全部价值都压在"证据是真的"上：一次 `read_file` 拿回来的
原文如果被我们改过，"这条论断指向这个文件的这一行"就不再可核对。

于是 `src/core/redact.ts` 只作用于**第一类**与**给人看的输出**（终端与 CI 日志是另一个泄漏面），
而两个入口各有各的守卫：

| 入口 | 堵的是 | 测试 |
|---|---|---|
| 适配器 | provider 把 key 回显进报错→`RunError.message`→事件日志 | `test/pi-adapter-sdk.test.ts` 的「脱敏接在错误分类之前」 |
| CLI 输出 | 被分析的仓库里恰好有个 key，被进度输出抄进 CI 日志 | `test/cli.test.ts` 的「脱敏」一节 |

CLI 那个入口做在 `main` 的 IO 包装层，而不是在每个打印点：**没有一处输出能忘掉它**。
而且那里的每条用例都拿**同一个字符串**同时断言两件事——输出里它被抹了、事件日志里它还在。
只测一句话是没有说服力的（"秘密没出现在输出里"可以只是因为输出里本来就没有它）。

## 五、十四个刻意做出的边界决定

### 1. `main(argv, io)` 是纯函数，`runCli()` 才是入口

所有与进程有关的东西（`argv` / `stdout` / `env` / `cwd` / SIGINT / stdin）都只在
`runCli()` 里出现一次，并作为 `CliIo` 注入。

理由不是好看：本项目的第一个不变量是"Core 能在没有进程、网络、数据库的情况下跑完"，
而**一个 CLI 恰好是最容易把这句话作废的地方**——它在 `main` 第一行读 `process.cwd()`，
之后所有东西就都绑死在进程上了。把 IO 注入进来，`test/cli.test.ts` 就能在一个进程里
跑完整的 `kuse run`，断言退出码、stdout 的形状、以及凭据有没有流进日志。
**产品面同样可以是可测的。**

### 2. SDK 在**校验全部通过之后**才被动态加载

`kuse trace` / `kuse runs` / `kuse sessions` / `kuse help` 一行 SDK 代码都不加载；
`kuse run` 也要等选项、任务文本、会话 id 全部校验过之后才 `await import(...)`。

这是"SDK 只在适配器后面"这条边界在**加载时间**上的体现。它有一个实测数字：

| | 改之前 | 改之后 |
|---|---|---|
| `kuse help` | 0.10s | 0.10s |
| `kuse run --sesion x`（选项拼错） | **1.50s** | **0.11s** |

SDK 建 provider 目录实测约 1 秒，而一次用法错误根本用不到模型。
"打错一个字"不该变成"等一秒钟"——这不是性能优化，是一条边界在时间轴上的样子。

### 3. 解析器要由子命令告诉它哪些选项**取值**

只靠语法猜（"后面跟着另一个 `-` 开头的词就是开关"）会**静默吃掉位置参数**：

```text
kuse run --offline 这个仓库里有哪些 TODO？
           └────────── 被当成 --offline 的值 ──────────┘
```

结果是 `--offline` 看起来没生效，而任务凭空消失——一次**不报错**的失败。
所以 `parseArgs(argv, { valued })` 的第二个参数是**词性**：哪些选项吃掉后面那个词，
由认识这些选项的那一层（子命令）说出来。解析器不需要知道 `--json` 是什么意思，
只需要知道它是开关。

配套的一条：`--store` 被写成一个裸开关时**报错**而不是用默认值。用户的意思显然不是
"用 `./runs`"，而是"我刚才少打了点东西"。与拼错的选项一样，这条也要报错而不是猜。

### 4. 一个开关可以吃掉位置参数，但**不许**在没有证据时猜测

上一条的另一面：`flagsMissingValue` 只对**声明过要取值**的选项生效。这不是校验的重复，
是同一个判断在解析层的落点——`--repo` 缺值时它是 `true`，而 `true` 不是路径。

### 5. 退出码与「Run 的结局」之间只有一处映射

`exitCodeFor(trace)` 是唯一的映射点，`unfinished` 落到 `internal`：
一次 `run()` 返回之后日志里必须有个结尾，没有就说明**我们没把这次 Run 走完**——
那是我们自己的问题，不是用户的 Run 失败。这条区分让 3 与 11 语义不同。

### 6. `RunStatus` 与 `RunTrace.stop.status` 是两件事

| 字段 | 取值 | 回答 |
|---|---|---|
| `trace.status`（`RunStatus`） | 六个：`queued` / `running` / `awaiting_human` / `completed` / `failed` / `cancelled` | **走完了没有** |
| `trace.stop.status` | 两个：`complete` / `partial` | **走得完不完整** |

所以一次"有结论但缺材料"的 Run 在 `status` 上是 `completed`。
把 `partial` 塞进 `RunStatus` 会让恢复逻辑把一个**已经交付了结论**的 Run 当成"没走完"
重新拾起来，那是最不该发生的一类重复劳动。

### 7. trace 不重算任何 Runtime 已经数过的东西

"花了多少"的答案是 `usage_reported` 事件本身。这里不做 token 加法、不数工具次数、
不重算时长——那些数字由 Runtime 在事件产生的那一刻记下，**重算一遍就会多出一个会与它分叉的真相**。

日志里没有那条事件时，诚实的答案是 `usage: null`（"这次 Run 没有账目"），
而不是我们自己算一个看起来差不多的数。`render.ts` 把它印成"provider 未报告"而不是 `0`。

### 8. `unfinished` 是第三种状态，不是 error 也不是 success

`tool_started` 写下了、而 `tool_completed` 没有——调用在途中 Run 就结束了。
归成 `error` 会让它看起来像"工具报错了"，归成 `success` 是撒谎。
所以 `TraceStep.status` 有三个值，而第三种只在这一个情形下出现。

### 9. 核对的判据是**包含**，不是重叠

读过 7-8 行而引用 1-40 行**没有被支撑**。用重叠会放过后者，而
"我读了那两行，所以我可以说整段话"正是要防的那种夸大。

路径也要归一化（`./a` 与 `a` 是同一个东西，Windows 上分隔符可能不同）。
`lines: null`（整文件级引用）只要那个路径被看到过就算支撑；反过来，
只列过目录（`list_dir`）**不能**支撑一个指向具体行的引用——列目录只说明路径存在。

### 10. 材料的知识住在工具那里，位置在 Runtime

「看到过哪些路径的哪些行」只有**工具自己**说得清：`read_file` 的返回里有 `path` 与行窗口，
`search_text` 的每条命中带一个行号，`list_dir` 只说明了路径存在。
所以这个知识是 `ToolSpec.material`，而核对器只接收一个**已经抽好的清单**——
Runtime 不需要、也不该知道任何一个工具的名字。这与步 8「schema 住在工具自己那里」是同一条理由。

`MaterialReader` 是这条接缝的类型：**位置**（谁什么时候调用）属于 Runtime，**策略**
（返回值的哪两个字段是行号）属于工具。

### 11. 截断把核对从「没看过」降级成「没找到」

截断是**替换**（步 6 的决定 6）：超过 `OBSERVATION_CHAR_LIMIT` 之后 `value` 变成一段文本预览，
原来的结构就没了。于是我们**看不到那条结果里到底有哪些行**。

不加这个字段的后果是实测撞出来的：一次 `search_text` 结果被截断，核对器于是把一条本该成立的
引用报成"没有任何一次调用看到过这几行"——一句**不成立的指控**。

所以 `EvidenceAudit` 有两个字段描述这件事：

- `truncatedObservations`：被截断的观测条数（在**抽取之前**数，因为截断之后抽出来的必然是空，
  而"抽不出来"不等于"没看到"）；
- `conclusive`：这次核对是不是确定的。`false` 时 `unsupported` 里的条目仍然值得看，
  但它们的意思从"没看过"降级成"在我能读到的材料里没找到"。

两种说法对应两种行动（前者要改模型，后者要缩小结果），所以**连打印的措辞都跟着降级**：

```text
  ? 有 1 条观测超长被截断，结构已丢：上面的条目只能读作"在能读到的材料里没找到"，不是"没看过"
  ? src/loop.ts:1-1 —— 在能读到的材料里没找到（有材料被截断，看不见）
```

### 12. Run 不许读到自己的产物

这条是**实测撞出来的，而且撞在默认配置上**：`--repo` 默认当前目录、`--store` 默认 `./runs`，
于是存储就在被分析的仓库里面；而事件日志里写着任务文本（还有搜索的模式），
所以一次 `search_text` 会命中**这次 Run 自己的日志**。

第一次跑出来是这样的——报告的第一条证据是它自己的 `events.jsonl`：

```text
   1. 按模式「assertSafePathSegment」在仓库里搜到 5 行命中
        证据 runs/run_c2db0902-…/events.jsonl:8-8
        证据 runs/sessions/sess_e56c29f0-….json:10-10
        证据 src/store/run-log-jsonl.ts:65-65
```

那是自指的：Run 把它的输出当成了它的输入，而且下一次运行会看到上一次的日志，越滚越多。

修法是 CLI 同时知道 `--repo` 与 `--store`，于是它能算出存储目录是不是在仓库里，
把那条**仓库相对路径**交给工具集去跳过（`createRepoTools({ ignore })`）。
跳过的是**路径**而不是目录名：用名字会让一个真正叫 `runs` 的素材目录被静默漏掉，
而"静默漏掉材料"看起来就像那个仓库里没有那些文件——这个项目最不愿发生的一类错误。

### 13. 被跳过的目录仍然可以被**显式** `read_file`

`ignore` 的作用范围是**发现**（`list_dir` / `search_text`），不是"禁止访问"。
拦在 `read_file` 上也行，但那只是把同一条限制在另一个地方再写一遍，
代价是 `read_file` 的行为开始取决于一个与它无关的清单。今天选择的是：
**我们不推给模型，但模型明确要了就给它。**

### 14. 只读路径把「不可能的名字」当「没找到」

`assertSafePathSegment` 在写入路径上抛错是对的（往一个坏名字里写是调用方的错误），
但**读**一个坏名字只是没找到。让它在只读路径上抛出去，会把用户的一次手误
（`kuse run --session 'a/b'`）报成"内部错误 3"，而脚本据此分不清"重试有用"与"参数得改"。

所以 `SessionStore.load` 对不可能的 id 返回 `null`，判据与写入路径共用同一个
`assertSafePathSegment`，于是"能写进去"与"能读出来"不可能分叉。

### 编译期验证

- **`TraceStop` 的穷尽性**：`exitCodeFor` 与 `stopLine` 的 `default` 分支里那个 `never`
  让"多一种收场"变成编译错误，而不是落进一个默认分支。
- **`AgentEvent` 的穷尽性**：`traceOf` 与 `progressLine` 各有一处 `never`——
  步 2 的词汇表长了，处理它的两个地方必须跟着长。
- **退出码 ↔ 码表**：`ExitCode = (typeof EXIT)[keyof typeof EXIT]` 让 `EXIT` 的对象字面量
  与类型绑死，加一个码不会漏掉类型。
- **SDK 的类型只在两处出现**：`type AdapterModule = typeof import("../adapter/pi/index.js")`
  与 `buildModel` 的参数。删掉 `src/adapter` 之后它们才报错——这是"SDK 只住在适配器后面"

## 七、刻意推迟的东西

| 推迟的 | 推迟到 | 理由 |
|---|---|---|
| 真机验证（真 provider、真凭据、真网络） | 有凭据的那一步 | 与步 8 同一条。`--model provider/model` 的解析、凭据检查、错误消息都写好了，**但没有凭据就没有真机会话**。今天能证明的是"命名与校验成立"，不是"接上某个具体 provider 也对" |
| `ask_human` 的回答怎么进来（`human_input_received` / `run_resumed` 的语义） | 有交互面的那一步 | 回放对这两条事件抛错、trace 不抛、CLI 的退出码是 13——三处都已经为它留好了位置，而"人的回答怎么进 transcript"是一个**语义**问题，不是接线问题 |
| 成本（`cacheRead` / `cacheWrite` / 价格表） | 有价格表的那一步 | 与步 8 局限三同一条 |
| 核对"结论在语义上对不对" | 需要另一个模型时 | 今天核对的是"这些行我们真的看到过吗"，那是**可确定**的。判断论断本身的对错需要第二个循环，而它需要的材料（`claims` 与观测）今天都齐了 |
| 流式进度（把 `onEvent` 的增量读成人能看的） | 有需求时 | 适配器已经把事件交出去了（`onEvent` 观察者），`progressLine` 今天读的是**产品级事件**，粒度够用 |
| 金标语料（golden transcripts） | 步 10 | `sequentialIds` 与离线 provider 都是为了它。退出码与 trace 的形状是它要比对的东西，所以它必须排在后面 |

## 八、局限（如实记录）

1. **`--model` 的真机路径没有执行过一次。** `resolveProviderModel` 的三步校验（语法 → provider 存在 → 凭据齐）在离线目录上验证过（41 个 provider、0 个凭据），
   但**一次成功的真机请求都没有**。所以 `kuse run --model openai/gpt-…` 今天能证明的是"报错报得对"，不是"跑得通"。
2. **退出码 13（挂起）在真机路径上到不了。** 离线 provider 只走 `submit_report`，
   没有一条到 `ask_human` 的流程。13 这个码由 `traceOf` 的单元测试守着，不是端到端守着。
3. **证据核对只核对"看没看过"，不核对"引用得对不对"。** 模型可以引用一个它读过的区间，
   却在 `excerpt` 里写一段那段区间里没有的话——今天**没有被发现**。`excerpt` 是模型给的字符串，
   核对器不看它的内容。补它需要在 `auditReport` 里对 `excerpt` 做子串比对（材料里存着原文），
   但那一刻的取舍是"先不误报"。
4. **`ignore` 只作用于发现，`read_file` 仍能读到被跳过的路径。** 这是决定 13 的代价：
   一个知道存储路径的模型仍然可以把 `runs/…/events.jsonl` 读成材料，那次核对会通过。
   今天不可达（离线流程只读搜索结果的第一条命中，而搜索已经跳过它），但它不是结构性地不可达。
5. **`search_text` 的命中上限与截断是一对张力。** 离线 provider 靠 `maxMatches: 5` 避开截断，
   但那是一个**消费者的自觉**，不是结构性保证：任何一次不限条数的搜索仍然会被截断，
   而截断之后离线流程会读到"0 条命中"（那个假相已经在 `faux.ts` 里留了注释）。
   `conclusive` 让核对**说实话**，但没有阻止那次流程走错。
6. **`kuse trace` 不做核对。** 只读模式没有仓库上下文（它只知道存储目录），所以它把 `audit`
   报成 `null` 并说明"未做核对"。这意味着**同一份日志用两条命令看会得到不同长度的报告**，
   而"核对过没有"这件事必须由读的人注意那两行字。
7. **`Clip` 的长度是猜的。** `clip(text, 96)` 这类上限会让一条长论断被截断成"…"，
   而截断标记**不在**那行文字里——人看不出这是原文的结尾还是被剪了。
8. **`--json` 的输出没有版本号。** 它的形状（六个键）今天由一条测试钉住，
   但一个把它当接口的脚本没有任何办法声明"我要的是这一版"。
9. **`main` 的 redaction 包装会重扫每一行输出。** 每次 `out`/`err` 都跑一遍全部字面量与六条形状正则，
   而输出可能是几千行进度。今天没有性能问题（一次 Run 的输出远小于这个量级），
   但它是 O(行数 × 规则数)，不是常数。
10. **`bin/kuse.mjs` 需要先构建。** 它 import 的是 `../dist/`，所以从零克隆之后
    `node bin/kuse.mjs` 会失败，必须先 `npm run build`。没有做"源码直跑"的兜底（那需要一条
    与构建产物不同的加载路径，代价比收益大）。
