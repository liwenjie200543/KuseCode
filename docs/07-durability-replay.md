# Step 7 — 事件日志是唯一真相，回放幂等

> 这一步的声明（见 README 开发序列）：**事件日志是唯一真相，回放是幂等的。**

本文回答的是「日志落在哪里、以什么形状」，以及「为什么回放与实时执行不会分叉」。

## 一、日志长什么样

```text
<rootDir>/sessions/<sessionId>.json    会话索引：这个会话有哪几次 Run（以及各自的 Task）
<rootDir>/<runId>/events.jsonl         事件本身：一行一条，换行终止，只追加
```

生产里的 `<rootDir>` 是 `runs/`，它已经在 `.gitignore` 里——**证据不进仓库**（见局限一）。

一次「工具之后应答」的 Run 写下的文件，逐行就是这样：

```text
{"type":"run_started","runId":"run_…","sequence":0,"timestamp":…}
{"type":"model_requested","model":"…","runId":"…","sequence":1,…}
{"type":"decision_made","decision":{"kind":"call_tool",…},"runId":"…","sequence":2,…}
{"type":"tool_started","toolCallId":"…","toolName":"read_file",…,"sequence":3,…}
{"type":"tool_completed","toolCallId":"…","status":"success","result":…,"durationMs":0,…}
{"type":"observation_added","name":"read_file","observation":{…,"provenance":{…}},…}
…（再一轮 model_requested / decision_made）
{"type":"run_completed","status":"complete","result":{…},"missingMaterial":[],…}
```

## 二、回放是一次折叠，不是一份等价实现

`replayAgentState(events, task)` 只做一件事：按 `sequence` 顺序把事件折进状态，每一次推进都调用**步 3 的 `reduce`**（`src/core/loop.ts`）。它没有第二套「把决策应用到状态上」的代码——这是整条链上最关键的一处复用：三份实现（实时执行、回放、单元测试）共用同一个纯函数，「回放重建出完全相同的状态」是**结构事实**，不是一条需要在测试里碰运气的纪律。

折叠规则只有三条，其余事件都不改状态：

| 事件 | 对状态做什么 | 为什么 |
|---|---|---|
| `decision_made { call_tool }` | **什么都不做**，只把意图记在一边 | 实时循环第一次产出时也没有推进状态（见边界决定 5） |
| `observation_added` | `reduce(状态, 那个意图, 这条观测)` | 一次调用对状态的推进恰好发生在观测到位的那一刻 |
| `decision_made { respond \| ask_human }` | `reduce(状态, 这个决策)` | 终态决策只产出一次，也就只推进一次 |
| 其余 | 什么都不做 | 它们记录「发生过什么」，不是「状态变了」 |

由此得到一条很有用的性质：**日志的任意前缀都是一个合法的恢复点。** 前缀长度 k 的状态里，`iteration` 恰好等于「终态决策数 + 观测数」，`transcript` 恰好是 `iteration + 观测数`。测试把这条等式在**每一个前缀**上都跑了一遍——它不是「另一种实现」，而是状态形状的定义。

## 三、九条刻意做出的边界决定

### 1. 「记录」的边界是换行符

一行写完才写换行（内容与换行在同一次 `appendFile` 调用里，内容在前），于是：

- **有换行符的行一定写全了**——因为换行是那次写入的最后一个字节；
- **没有换行符的尾巴从来不是记录**——它是一次写了一半的崩溃残骸。

读的时候丢掉残骸（它不产生半个状态）；下一次追加之前先 `truncate` 掉它。清理残骸不违反「只追加」，因为它不是历史——恰恰相反，**不清理才会真的丢东西**：下一条记录会和残骸粘成一行，一次损坏变成两条事实同时消失（破坏性验证时看到的正是这个：`第 4 行不是合法的 JSON`）。

推论是第二条：**一条被换行终止、却解析不了的行，只能是被外部改过或者磁盘出了问题**，所以它是**损坏**，必须响亮地报出来，而不是当成残骸顺手跳过。

### 2. `read` 直接读磁盘，而且用的是同步 API

契约里的 `read(runId)` 是同步签名（步 4 定形，那时没有载体）。而**恢复恰恰发生在一个从没 `append` 过的进程里**——用「本进程写过的内存副本」回答读请求，等于让「事件活下来」这件事不成立。所以 `read` 用 `readFileSync`：恢复是一次启动时的动作，没有并发要等，同步不是偷懒，它就是这条声明成立的那一步。

`append` 走的是另一条路：它记着「这个进程最后一次读到的序列」，于是追加是 O(1) 而不是每次重读整个文件（O(n²)）。这条捷径的代价是一条明确的契约——**一个 Run 只有一个写者**（Runtime 的 `emit` 是串行的）。并发写同一个 Run 不在契约里，也不假装在。

有一条测试专门钉住「读走磁盘」这个决定：第二个实例（另一个进程的替身）刚写下的事件，第一个实例读得到——它缓存里没有那一条。

### 3. 序列化往返是日志的最后一道关

写下去之前，`JSON.stringify` 之后再 `JSON.parse` 回来比一次，不相等就拒绝写入。步 6 的那道关（`docs/06-tool-execution.md` 边界决定 6/8）守的是「工具的返回值能不能进状态」，这一道守的是「**一条事件能不能进文件**」——`decision_made` 里带着模型给的 `ToolIntent.args`，它**在工具开跑之前**就已经落日志了，那时步 6 的关卡还没经过。两个对象、两个时机，判据是同一条：JSON 装不下的东西不能进日志。

它抓的是 JSON 那些**安静**的变化：`undefined` 丢键、`NaN` 变 `null`、`Map` 变 `{}`、函数直接消失。静默地改变一条证据，比拒绝写下它糟得多——因为它看起来像是这条材料本来就没有那一部分。

### 4. 会话索引只存日志答不出来的东西

索引里只有两样：**哪些 Run 属于这个会话**，以及每个 Run 的 `createdAt` 与 `Task`（`run_started` 的载荷是空的，步 2 定的词汇如此，`docs/04-run-events.md` 局限二记着这件事）。

`Run.status` / `startedAt` / `updatedAt` **不存**，全部从日志派生。这不是省事，是这一步最重要的一条纪律：**存一份「运行到哪了」就等于多一个真相，而它与日志分叉的那一天没人会收到通知。** 派生的状态不可能与日志不一致，因为它就是从日志算出来的。破坏性验证里把 `status` 换成一个常量，两条测试立刻失败——一次**从没跑过**的 Run 会宣称自己 `completed`，于是它从「还没走完」的清单里消失了。

代价是 `getSession()` 会读每个 Run 的日志。会话视图不是热路径，而「先读日志、再回答」正是恢复该有的样子。

### 5. 意图不当场推进状态（照抄实时语义）

`decision_made { call_tool }` 在回放里**不**推进状态：实时循环的第一次产出交出去的还是进入这一轮的状态，`reduce` 是执行结束之后才调用的。回放要是当场推进，同一轮会被算两遍（`iteration` 多一、transcript 多一条空的意图）。所以这条规则不是选择，是照抄。

这个选择的代价见局限二，它同时**证伪了步 6 留下的一条预测**：`collectMissingMaterial` 的第三条来源（有意图、无观测）不能通过回放到达，因为 transcript 里永远不会出现「assistant 的 `call_tool` 没有配对消息」这个形状——`reduce` 只在观测到位时被调用一次。今天到达那条分支的唯一办法是手工构造状态（步 6 的单元测试就是这么做的）。这个发现钉在 `test/replay-idempotence.test.ts` 里，后面要改它之前，先得想清楚恢复时「一条在途的调用」该以什么形状回到状态里。

### 6. 重建不了的事件，响亮地拒绝而不是跳过

`human_input_received` 与 `run_resumed` 会让回放**抛错**，理由一句话说得清：把人的回答写进 transcript（`role: "human"`）的那一步**不存在**——`reduce` 只接受决策。挂起与恢复的语义没落地之前，回放对这两条事件只能回答「我不知道」。

跳过会安静地重建出一个**少了人那一步**的状态，而它与「本来就没有人那一步」的状态在回放看来一模一样——那是「日志是唯一真相」最不能容忍的一种错误。**宁可拒绝，不猜。**

`runStatusOf(events)` 就没有这么严格：它只需要看终态事件，所以同一份含 `human_input_received` 的日志，回放拒绝它，而「这个 Run 停在哪儿」答得出来（`awaiting_human`）。这不是不一致——两个问题各自知道自己要什么，严格程度不同是它们应得的。

### 7. 身份先于运行存在，而且只交出去一次

要能从崩溃里恢复，Run 必须在**开始之前**就登记进会话（否则一次崩溃留下的是一份没有任何索引的记录）。所以 `startRun()` 先造 id、先落索引，再把这个 id 交给 Runtime——做法是把身份**钉住**（`pinnedIdentity`）：身份本来就可注入（步 4），于是存储能先定下它，而不必让 Runtime 知道存储的存在。

这个工厂**只服务一次 Run**：`runId()` 被问第二次就抛错。一个能反复给出同一个 id 的工厂，会让两次 Run 的事件写进同一份日志（第二条的 `sequence` 从 0 重来，第一条立刻被 `assertAppendOnly` 拒绝）——与其等日志报错，不如在问第二次的时候就直说。

**Runtime 一行都没改。** 步 4 把身份做成可注入的形状时并没有预见到这一步，是那个形状自己撑住了这件事。

### 8. 会话索引原子写，事件日志不原子写

会话索引是**会被重写**的（每加一次 Run 就重写一遍），所以「写到一半崩了」是它真实的失败模式：先写 `.tmp`，再 `rename`。改名是原子的，读者要么看到旧的完整版本，要么看到新的完整版本。

事件日志不需要这一手——它只追加，而「追加」的失败模式是尾部残骸，由边界决定 1 处理。**两种失败模式，两种修法**，没有一种万能写法可以同时对付它们。

### 9. I/O 只住在 `src/store`

这一步把「事件的载体」搬进了仓库，于是多了一条必须守住的边界：**Runtime 的语义里没有 I/O。** 回放从事件重建状态、预算执法、事件排序都是纯粹的推导，它们一旦自己去读文件，「同一个日志重建出同一个状态」就取决于磁盘上那一刻有什么了。

所以 `test/no-runtime-deps.test.ts` 新增两条断言：`src/runtime` 零 `node:` 引用；`src/` 下面所有 `node:` 引用都落在 `src/store` 里。这两条在此之前**本来就是真的**（步 3~6 的 runtime 一行 I/O 都没有）——这一步只是把它从一句会慢慢失效的描述，变成一条可执行的约束。

`test/replay-idempotence.test.ts`（30 条）覆盖：

1. **回放 === 实时**——五条路径（一趟收工 / 工具后应答 / 两次调用 / 问到人 / 取消在调用中途）各断言一次：`replay(log.read(runId), task)` 与**同一段脚本**跑出来的实时循环状态深相等。

## 五、刻意推迟的东西

| 推迟的 | 推迟到 | 理由 |
|---|---|---|
| `human_input_received` / `run_resumed` 的重建 | 恢复语义落地的那一步 | 回放**拒绝**它们（边界决定 6）：`reduce` 只接受决策，「把人的回答写进 transcript」这一步不存在。要有它，得先回答「挂起的 Run 被叫醒之后从哪继续」 |
| 「在途的调用」如何回到状态里 | 同上 | 见边界决定 5 与局限二。今天它只存在于日志里，不在状态的投影里 |
| `usage_reported` | **step 8 已落地，回放一行没改** | 表里已经表态为「不影响状态」（它是账目），所以步 8 不必回来改回放——**这条预测成立**，`replay.ts` 一行都没动（`usage_reported` 不在折叠规则里）。重试也一样：它改写的是「事件流怎么发生」，不是「事件说了什么状态」 |
| `traceOf` 与前缀检查的复用 | **step 9 已落地** | 那条「输入必须是从头开始的连续前缀」的检查从 `replayAgentState` 里抽出来成了 `assertContiguousPrefix`，因为 trace 读的是同一份日志、回答的是同一层面的问题（"这串事件说的是哪一次 Run"）。**抽出来时消息顺便写清楚了**：它现在报出实际看到的 `sequence`，而不只是说"不对"。trace 与回放只有一处**刻意不同**——它对 `human_input_received` / `run_resumed` 不抛错，因为它不重建状态、只读事实（`docs/09-cli-trace.md` 一、决定 5） |
| trace 渲染 | **step 9 已落地** | 把日志读成人能看的东西，是产品面的事：`src/cli/render.ts` 是与 `src/runtime/trace.ts` 分开的，因为"停止原因是 `cancelled`"与"那一行印成了 `cancelled（被取消）`"是两件需要各自被钉住的事 |
| 会话的其它操作（列出全部会话、删除、归档） | **「列出全部会话」step 9 已落地**（`kuse sessions`），其余仍未做 | 落地的那一条印证了原来的理由：它是**因为有了消费者**才做的（`kuse sessions` 需要"有哪些会话"），而且它落在 `SessionStore.listSessions()` 而不是让 CLI 去 glob `sessions/` 目录——目录布局是存储的实现细节，让产品层依赖它等于把布局冻结成公开契约。删除与归档仍然没有消费者 |

## 六、局限（如实记录）

1. **`runs/` 在 `.gitignore` 里，证据不进仓库。** 这条是刻意的（运行产物不是源码，golden transcripts 要显式提交），代价是「一次真实运行的日志」默认只留在本机——要给别人看必须明确地拷出去。
2. **回放重建出的是「已经完成的那些推进」，不含在途的调用。** 一次崩溃在工具调用中途的 Run，恢复出来的状态里没有那条意图（它只在日志里）。这是照抄实时语义的直接后果，也是「不能靠回放到达步 6 第三条来源」的原因。要改它，得先有恢复语义。
3. **单写者契约。** 同一个 Run 的日志并发写不在契约里：`append` 用的是「这个进程最后一次读到的序列」，一个并发的写者会让它写出重复的 `sequence`（随后被日志自己的连续性检查拒绝——响，但晚了一步）。
4. **`getSession()` 是 O(Run 数 × 事件数)。** 每个 Run 的 `status` 都要读一遍它的日志。会话视图不是热路径，但一个会话里攒了几千次 Run 之后，这个调用会变慢——那时该加的是索引缓存，而不是把状态存回去。
5. **`read` 是同步的，大日志会阻塞事件循环。** 一次 Run 的日志有界（截断上限 + 预算上限，步 5/6），所以今天没问题；真要读一份几十 MB 的历史日志时，这个签名会先咬人。
6. **残骸的清理只发生在追加路径上。** 一个只有 `read` 的进程（纯恢复、不接着跑）不会去截掉残骸——它每次读都要重新丢一次那条尾巴。这是对的（恢复不该有副作用），但值得知道。
7. **`recover` 只认 `(sessionId, runId)`。** 它不去扫全部会话找 Run：Run 属于某个会话是这一步的隔离契约，绕过它去找一个 id 会把「隔离」变成一句好话。
8. **只有假通道。** 「另一个进程」在测试里的替身是「另一个实例」，不是真的重启进程；`fsync` 也没有做（`appendFile` 之后由操作系统决定何时落盘），所以「机器断电」这一档，这一步只覆盖到「进程被杀掉」。
