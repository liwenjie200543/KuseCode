# Step 5 — 预算与取消让 Run 可预测终止

> 这一步的声明（见 README 开发序列）：**Runs terminate predictably; cancellation stops
> future work.** 一次 Run 要么走完，要么在一个说得清的地方停住；停下来之后，不会再发起
> 任何调用。

本文回答的是「为什么停止这件事长这样」，不是「怎么调 `run()`」。每加一条约束之前，
先回答它守住了哪条第一性原理；回答不出来的约束就是过早抽象。

## 一、停止有三个入口，但只有一个含义

| 入口 | 触发者 | 日志里收尾于 |
|---|---|---|
| 外部取消 | 调用方（人按了停） | `run_cancelled` |
| 墙钟到点 | 我们自己（预算里的 `timeoutMs`） | `run_failed{budget_timeout}` |
| 消费者离场 | 消费事件流的一方（`for await ... break`） | `run_cancelled` |

前两条共用一条信号，第三条不是信号——它发生在生成器被关闭的那一刻。它们共用的不是
代码路径，是**同一个含义：这次 Run 不会再做任何事。**

第三条是步 4 留下的「没有名字的结局」。步 4 的记录是：消费者提前 break 时，日志停在
半路、没有终态事件，而本步能保证的只是「日志不被消费者破坏、它看到的是前缀」。
本步给了它一个名字，因为一个没有结尾的日志与一个崩掉的日志在回放（步 7）看来是同一
件事——**「没有结尾」必须是一个显式状态。** 区别只有一个：这一条写得下，但没人看得见
（消费者已经走了）。日志是唯一真相，真相要收尾；事件流是它的投影，投影停在消费者离场
的那一刻。

于是本步之后，**每一次 Run 在日志里都停在一个有名字的地方**：终态事件
（`run_completed` / `run_failed` / `run_cancelled`）恰好一条，或者一条
`human_input_requested`（挂起，它还活着，所以不该有终态事件）。步 4 的表述是
「respond / 失败两条路径各以恰好一个终态事件收尾」；现在这句话对**所有**路径成立，
挂起那条只以「有名字的停点」收尾。

## 二、预算归 Runtime：三个检查点，都站在动作之前

Core 里没有一行预算代码——步 3 用一行编译期证明守着这件事，本步没有去动它。
执法全部在这一侧，位置如下：

| 检查点 | 位置 | 什么时候 | 拦下什么码 |
|---|---|---|---|
| `beforeModel(state)` | 模型端口的包装层 | 每次问模型之前 | `no_progress`、`budget_iterations` |
| `beforeTool(intent)` | 驱动方的**意图点** | 收到「模型要调工具」之后、`tool_started` 之前 | `budget_tools` |
| 墙钟 | 组合信号（`termination.ts`） | 任意时刻 | `budget_timeout` |

三点说明：

1. **检查在动作之前，不是之后。** 事后检查等于「超支了再说」：那次调用已经花掉了钱，
   而且可能已经写下了一个文件。所以「超限」的最强形式是**那次调用根本没有发生**——
   测试用假适配器的计数断言这一点，而不是看事件流（一个偷偷又调了一次的 Runtime
   可能仍然长得对，那次调用只是没进事件）。
2. **取消的检查也在动作之前，而且有两道。** 一道在动作的决定点（和预算同一个位置），
   一道在端口包装层、紧贴调用的那一刻。第二道守的是一个很窄的窗口：检查与调用之间
   还有几个 `await`（落一次日志、送一次事件），取消恰好落在那里的话，本来会有一条调用
   被发出去。有第二道之后，「中止之后不再发起任何调用」不依赖「希望每个适配器都记得
   看信号」，而是结构性的。测试用「日志在做完 `tool_started` 的追加时把 Run 取消掉」
   精确地打中这个窗口。
3. **工具预算的账记在「意图点」，不记在端口包装层。** 这不是实现便利，是修一个被实现
   抓出来的缺陷——见下一节。

### 被实现抓到的一个缺陷：`tool_started` 说过谎

第一版把工具预算检查放在工具端口的包装层（与模型那一侧对称），看起来更自然。
探针打出来的事件流是这样：

```text
run_started | model_requested | decision_made | tool_started | tool_completed | observation_added
          | model_requested | decision_made | tool_started | tool_completed | observation_added
          | model_requested | decision_made | tool_started | run_failed
```

`tool_started` 出现了三次，而工具只执行了两次——第三条属于一次**从未开始**的调用。
事件流里「有 `tool_started`、没有 `tool_completed`」本来是步 4 定义的有意义的状态
（有意图、结果没回来），但在这里它是假的：那次调用不是被打断的，是被我们自己拦下的，
而且**拦下之前我们就已经在日志里写下了「开始了」**。

修法是把检查挪到驱动方看到「模型要调工具」的第一刻——它在 `decision_made` 之后、
`tool_started` 之前，是最后一个既能拦住调用、又还没落笔的位置。移动之后，
被拒的那一轮事件流里只有 `decision_made`，一句话都没多说。端口包装层保留的
是纯取消检查（不记账），所以账只记一次、事件只写一次。

### 一个必须付的价

工具预算会让这次 Run **多问模型一次**。原因不是疏忽：不问就不知道下一个决策是不是要
调工具。所以 `maxToolCalls` 与 `maxIterations` 的关系是「宽的那个先到、窄的那个多花
一次模型调用」，测试里把 `model.calls === 3` 与 `completed === 2` 一起钉住了——
数字上的不对称是事实，不该被藏起来。

## 三、归因靠信号，不靠错误的形状

一条信号响了，驱动方要说得清是「人按了停」还是「我们的墙钟到点了」。判据只有一条：
**问我们自己那条信号的来源，不看抛出物长什么样。** 端口在中止时抛什么
（`DOMException`、`AbortError`、provider 自创的异常）是 provider 的词汇，
Runtime 一个都不认。

于是 `createRunSignal` 把两个来源合成一条交出去，同时各自留一个可识别的身份，并且
**先响的说了算**（同时响时外部优先——那是人的决定，比我们自己的时钟更该被报告）。
组合有三条不变量：

- 总有一条：调用方没传信号、预算也没设墙钟时，仍然交出一条永不中止的，
  「这条 Run 不会因信号而停」是一个显式事实，不是某个 `??` 的副作用；
- 只有一个来源时不做包装：交出去的就是那条信号本身；
- `dispose()` 摘掉监听器（幂等）。它**不能**取消已经设下的墙钟定时器——
  `AbortSignal.timeout` 没有公开的取消接口。代价是到点空转一次监听器调用，
  而不是把进程拖住：这条是实测过的（设了 3 秒超时之后进程 3ms 正常退出，
  定时器是 unref 的）。

两个码必须分开：`budget_timeout` 是**这次 Run 的墙钟**，`timeout` 是**单次请求的超时**
（步 6/8）。合成一个码，trace 就答不出「是谁的时间到了」——**步 9 的 `TraceStop.kind === "failed"`
原样带着这个码**，所以那条区分一路走到了退出码 11 与它印出的那一行（`docs/09-cli-trace.md`）。

## 四、六个刻意做出的边界决定

### 1. `no_progress` 的执法到位了，但它在今天的 Core 里不可达

这是本步最值得写下来的一件事。步 5 给它的检查写了、测了，但**在今天的 Core 里它触发
不了**，原因是结构性的：

> 一次 `call_tool` 必然往状态里写一条观测（`reduce` 干的），所以「这一轮没有增加任何
> 观测」不可能发生。Core 的 `hasProgress` 数的是观测**数量**，而数量每轮都 +1。

真正的空转长的是另一个样子：**每轮拿到一模一样的观测**（反复读同一个文件、反复跑同一
个 grep，结果一字不变）。步 3 的文档已经预言了这个缺口，本步把它变成了可执行的事实：

- 一条测试钉住今天的语义（反复读同一个文件、结果相同 → 仍然算前进 → 停下来的原因是
  迭代预算，不是空转）；
- 一条测试换上**更严的谓词**（「信息上有没有新的」：同 `tool` + 同 `value` 不算新），
  同一段脚本立刻被认作空转 → `run_failed{no_progress}`，且此后一次调用都没有；
- 第三条测试钉住更严的谓词的**边界**：结果真的变了仍然算前进——否则它就成了
  「关掉 Agent 的开关」。这个方向的不对称是刻意的：漏判一次空转只是多跑几轮，
  误判一次会把一次健康的 Run 干掉。

所以执法是**接缝**（`progress` 谓词可注入），默认值就是 Core 的 `hasProgress`。
把谓词留在 Core 不动，是因为换掉谓词等于换掉「什么叫空转」的语义——那要有真实的
空转证据（一次真的跑飞了的 Run）才动，本步只有推测。

还有一个位置上的事实：空转只能在**轮边界**上被判出来（「这一轮带来了什么」要等它结束
才知道），所以从「第二次读到同样的内容」到「停下来」之间隔着一次模型调用。这不是延迟，
是唯一可能的位置。

### 2. token 预算本步**不执法**

`RunBudget` 里有 `maxInputTokens` / `maxOutputTokens`（步 2 的词汇），本步没有实现它们
的检查。两条理由，第二条是决定性的：

1. 没有 usage 来源——步 8 之前拿不到真实 token 数，任何检查都是拿 0 去比（**步 8 已补上**：`ModelPort.beginRun` 交出这次 Run 的账本，见 `docs/08` 决定 7）；
2. 更关键的是**没有对应的失败码**。`RunErrorCode` 里没有 token 类（步 4 用
   `satisfies` 把这张表钉死了，加码会当场编译不过）。硬塞成 `budget_iterations`
   会让 trace 说错停止原因：一次因为 token 花光而停的 Run 会被记成「轮数用完了」。

宁可留一个显式的缺口，也不让 trace 撒谎。加它的条件很清楚：有了真实 usage 时，连同一个新的失败码一起加。

**条件在步 8 满足，两样一起加了**：`budget_tokens` 进了 `RunErrorCode`，执法点是 `beforeModel(state, spent)`——它拿账本**现读**的用量去比，而不是拿一个缓存的数（缓存会让「这个 Run 花了多少」有两个答案）。一条必须记住的规则：**未知（`null`）永不算超限**。把「没测到」当成「没花钱」会放行一个可能已经超额的 Run，那比漏报更糟——所以不报数的 provider 不会因为这个预算被杀，而这件事在 `usage_reported` 里是看得见的（那两个数就是 `null`）。

### 3. 默认预算是**有界**的，而它仍然可以关掉

`createRuntime` 的 `budget` 是可选的，省略时用 `DEFAULT_BUDGET`（32 轮 / 64 次工具 /
10 分钟 / token 不限）。这与 `log` 必须由调用方指名并不矛盾：一个默认的日志会安静地
扔掉证据，而一个默认的预算只会让一次跑不完的 Run 停下来说清原因。想关掉某一条就显式
写 `Infinity`——那是调用方的选择，不是我们替他默认的。

数字本身是工程判断而不是推导，所以它们都写在一个地方、写得出处、改得动。

### 4. 组合信号改变了「交给端口的信号是哪一条」，步 4 的两条断言因此被改

步 4 有一条断言：模型与工具收到的就是调用方那条 `controller.signal`。步 5 之后交出去的
是**组合**出来的那条（外部取消 + 墙钟），所以在配置了 `timeoutMs`（默认配置就是）之后，
身份不再相等。

改的是断言，不是主张：那条测试真正要守的是「**两端拿到同一条**」——它才是取消能贯通到
端口的前提。身份相等只是当时那个实现恰好成立的性质。改动连同理由写进了测试注释，
另外两条新断言（中止能真的打断在途调用、中止后不再发起任何调用）在步 5 这里。

同一次改动还收回了步 4 里另外两条依赖旧行为的断言（`all.length === seen.length + 1`、
「提前 break 之后日志里没有终态事件」），它们表述的是**本步之前**的事实，
新的事实与它的证据一起搬到了 `test/runtime-budget.test.ts`。

### 5. 挂起不是结束，所以它不该被写上一个终态事件

`ask_human` 那条路径的最后一个事件是 `human_input_requested`，而 `settled` 标志在这里
就置位了。挂起是「还活着」（`RunStatus.awaiting_human` 本来就不是终态），把它写成终态
等于把一次等待答案的 Run 说成已经结束了。所以 `finally` 里那条补偿只在
「还没有走到任何停点」时才触发。这条分支有专门的测试——`settled` 是那种一旦写错就
静默出错的标志。

### 6. `dispose()` 与墙钟定时器：能摘的摘，不能摘的说清楚

`dispose()` 摘掉挂在两个来源上的监听器，幂等。它不能取消 `AbortSignal.timeout` 设下的
定时器（没有公开接口），但定时器是 unref 的，所以它不会把进程按在事件循环里不放。
`test/runtime-budget.test.ts` 有一条断言摘掉之后外部信号再响也不再改变归因——
这证明了 `dispose` 真的摘了，而不只是「看起来像摘了」。

## 六、刻意推迟的东西

| 推迟的 | 推迟到 | 理由 |
|---|---|---|
| 重试（`maxRetries` 已在词汇里，本步不消费它） | **step 8 已落地** | 重试要有「这个错误值不值得重试」的判断，而那需要 provider 的错误分类——映射表在 `src/adapter/pi/errors.ts`，政策在 `src/runtime/retry.ts`（只认归一后的码，一行 provider 词汇都没有）。**两个所有者，两张表。** 分类判据只有一句：重发能不能改变结果。 |
| token 预算的执法 | **step 8 已落地** | 见边界决定 2：当时没有 usage 来源也没有失败码，两样都在步 8 补上了（`ModelPort.beginRun` + `budget_tokens`）。 |
| 单次调用的超时、参数校验、结果截断 | step 6 | 它们属于执行层；今天假工具不做这三件事，`budget_timeout` 与 `timeout` 的分工在文档里说清了。**步 6 已落地**：`timeout` 有了第一个产生者（工具侧，被隔离成一条观测），而同一个码在模型侧仍然致命——**步 8 履行了这条**：适配器把超时归一成 `timeout` 抛出，它不落成观测、而是落成 `run_failed`。两侧后果不同的理由在 `docs/06-tool-execution.md` 边界决定 3。 |
| `human_input_received` / `run_resumed`（挂起怎么被叫醒） | 仍未落地 | 需要有「谁交回答案、怎么重新进入循环」的恢复入口，而恢复要先有持久化。**步 7 落了持久化，但没有落恢复**：回放明确拒绝这两条事件，因为把人的回答写进 `transcript` 的那一步状态推进不存在（`docs/07-durability-replay.md` 边界决定 6）。 |
| 重试次数、退避策略 | **step 8 已落地** | 同第一行。`maxRetries` 的所有者是 `RunBudget`（调用方说的话），退避参数是 `DEFAULT_RETRY`（我们的事）：250ms 起、翻倍、封顶 4s。不做抖动——单进程单 Run，没有收益的随机性只是噪声。 |

## 七、局限（如实记录）

1. **只有假通道。** 「适配器在信号中止时拒绝在途调用」这件事今天是 `inFlight` 这个假
   适配器在兑现。**步 8 在真适配器里兑现了这一条**：`signal` 原样交给 `pi-ai` 的流，而流在 `aborted` 时以 `stopReason: "aborted"` 收尾、**抛出的错误不带码**（归因权交回 Runtime——它手上有 `cause()`，分得清"用户取消"与"墙钟到点"，适配器分不清）。所以本步证明的是**执法结构性**，不是
   「真实 provider 一定会被我们打断」。
2. **`no_progress` 的触发条件不可达**（边界决定 1）。执法有效，但今天的 Core 里没有
   东西能让它响。**这是本步最应该被记住的局限**：一条不会敲响的警报，与一条没接的
   警报，在功能上是一样的——区别只在于我们知道自己没接。
3. **墙钟定时器无法取消**，只能等它到点（unref，不拖住进程）。一次短命 Run 用它，
   代价是一个到点空转的定时器。
4. **工具预算会让 Run 多问一次模型**（见第二节末尾）。
5. **`budget.timeoutMs` 到点的后果是「Run 失败」而不是「Run 挂起再续」。** 一个跑了
   十分钟的任务没有中间状态可恢复——恢复属于步 7。
   *（步 7 的追加：持久化到了，**恢复**没到。日志现在活得过进程、「哪些 Run 还没走完」
   也问得出来（`unfinished`），但把一次中断的 Run 接着跑下去仍然没有入口——
   缺的是「从某个状态重新进入循环」那一步，见 `docs/07-durability-replay.md` 第五节。）*
6. **时间只被用在墙钟上**：`durationMs` 仍是注入时钟的两次调用之差，事件的 `timestamp`
   同理。真实的墙上时间只在 `AbortSignal.timeout` 那一处出现。
7. **消费者离场补的那条 `run_cancelled` 没人能看见。** 只有日志读者（回放、trace）受益。
   如果将来要让 UI 知道「有人停了这次 Run」，那需要一个消费者之外的观察者，
   本步没有引入。
