# Step 6 — 工具执行层：输出不可信，失败被隔离

> 这一步的声明（见 README 开发序列）：**Tool output is untrusted; one failure does not
> corrupt state.** 一次工具调用要经过的每一道关，都建立在这句话的两个半句上：
> 「不可信」决定**要检查什么**，「不污染状态」决定**失败之后怎么办**。

本文回答的是「为什么执行层长这样」，不是「怎么调用 `createToolRunner`」。每加一条约束
之前，先回答它守住了哪条第一性原理；回答不出来的约束就是过早抽象。

## 一、一次调用要过的八道关

顺序就是代码里的顺序。**「后果」那一列是这一步的全部要点**：前两关拦下的调用从未发生，
从第三关起失败的调用就是一条数据。

| # | 关卡 | 位置 | 失败的形式 | 后果 |
|---|---|---|---|---|
| 1 | 名字在 allowlist 里吗 | `rejectIntent` | `invalid_tool` | 调用**从未发生** |
| 2 | 参数能进日志吗 | `rejectIntent` | `invalid_args` | 调用**从未发生** |
| 3 | 这次 Run 已经被停了吗 | 调用之前 | 抛出（不落观测） | 归驱动方，不是工具失败 |
| 4 | 这一次调用超时了吗 | 步 5 的组合信号 | `timeout` | 一条观测，Run 继续 |
| 5 | 交回来的是 `ToolOutcome` 吗 | `normalizeOutcome` | `tool_failed` | 一条观测，Run 继续 |
| 6 | 返回值能进日志吗 | `normalizeOutcome` | `invalid_result` | 一条观测，Run 继续 |
| 7 | 结果超过上限了吗 | `assembleObservation` | `truncated: true` | 一条观测（预览），Run 继续 |
| 8 | 来源与时刻由谁写 | `assembleObservation` | 工具伪造无效 | 观测带**我们**的 provenance |

`ToolOutcome → Observation` 的转换只发生在最后两关，也只发生在
`src/runtime/tool-runner.ts` 这一个文件里。**`src/core` 在这个步骤里一行都没有改**——
步 3 把 `assembleObservation` 留成接缝时预言过这件事（「步 6 把校验、超时、截断接进来时，
Core 不需要改一行」），这一步兑现了它。假适配器只动了一处签名（工具可以异步、可以拿到
取消信号），那是为了让「在途调用被信号打断」这件事在测试里表达得出来。

## 二、八个刻意做出的边界决定

### 1. 失败是数据，不是结局（唯一的例外是我们自己的停止信号）

一次工具失败在这个系统里的归宿是一条 `error` 非 null 的观测：Run 接着往下走，终态是
`partial` 加上点名缺失的材料。这么做的理由不是「容错」这种糊话，而是**价值不对称**：
一次已经跑了十分钟的 Run，不该因为某一次 `grep` 崩了就被判死刑——那条材料没拿到，
这件事可以如实报告，而报告本身仍然有价值。

所以执行层的 `catch` 里只有一个东西**不**被折算成观测：**我们自己那条信号的响动**。
判据与步 5 的驱动方完全一样——问信号，不看抛出物长什么样：

```ts
const cause = call.cause();
if (cause === "external") throw error;              // 这次 Run 被停了 → 交回驱动方归因
if (cause === "wall_clock") return failed("timeout", …);  // 我们自己的计时器
return failed("tool_failed", …);                    // 工具自己抛的
```

这一处复用的意义比省几行代码大：**同一个问题只有一套答案**。「中止时端口抛什么」
是 provider 的词汇，Runtime 在驱动方不认它，在更靠里的执行层也不认它。

### 2. 执行层的错误码不是 `RunErrorCode`

`TOOL_ERROR_CODES` 有五个码，`RunErrorCode` 有十个，它们**不共用**：

| 词汇表 | 回答的问题 | 谁在用 |
|---|---|---|
| `RunErrorCode` | 这一次 Run 为什么不干了 | `run_failed`（步 4/5） |
| `ToolErrorCode` | 这一条材料为什么没拿到 | `Observation.error` / `missingMaterial` |

一次工具失败**不会**结束 Run，所以它不该借用 Run 级的码。假如借用，`tool_completed` 上
就会出现一个 `rate_limited`，读者会以为 provider 把整个 Run 限流了——而实际上只是某个
工具自己撞上了限流。`invalid_tool` 是唯一两边同名的码，这不是遗留：Run 级的那个说的是
「这次 Run 停下来，原因在执行层」，工具级的那个说的是「这个名字不在 allowlist 里」。

### 3. `timeout` 与 `budget_timeout` 第一次真的分开了，而且后果不同

步 5 定下这两个码必须分开（「合成一个码，trace 就答不出是谁的时间到了」），但那时
`timeout` 还没有任何产生者。这一步给了它第一个：**单次调用的超时**。

| 码 | 指什么 | 后果 |
|---|---|---|
| `budget_timeout` | 整次 Run 的墙钟（步 5） | `run_failed`，Run 结束 |
| `timeout` | 一次工具调用（本步） | 一条观测，Run 继续 |
| `timeout` | 一次模型请求（步 8） | 大概率 `run_failed` |

同一个码在两侧后果不同，理由是**「这一条还能不要吗」的答案不同**：模型请求失败，就没有
下一个决策了，Run 无从继续；工具调用失败，只是少了一条材料。所以「一次调用超时」这件事
的性质不由码决定，由它挡在谁前面决定。

单次调用超时的实现直接复用了步 5 的 `createRunSignal`：外部（这次 Run 的信号）+ 墙钟
（这一次调用的计时器），**先响的说了算**。那次组合机制的第二个消费者一个参数都没改——
一个为「整次 Run 的停止」写的东西能原样用在「一次调用的停止」上，说明当时拆出来的
是「停止的形状」而不是「Run 的形状」。

### 4. 「能进日志」是这道边界的准入条件——参数与返回值用同一条规则

`findJsonProblem` 查的不是「能不能序列化」，而是「序列化会不会**安静地**改变它」：

| 值 | `JSON.stringify` 之后 | 为什么必须拦 |
|---|---|---|
| `{a: undefined}` | `{}` | 键被丢掉，看起来像「本来就没有这个键」 |
| `[1, undefined]` | `[1, null]` | 值被换成 null |
| `NaN` / `Infinity` | `null` | 同上 |
| `() => {}` / `Symbol()` | 键被丢掉 | 同上 |
| `new Map([…])` / `new Set([…])` / `new Error()` | `{}` | 整个内容没了 |
| 循环引用 | **抛错** | 会在写日志那一刻爆，而不是在数据进来那一刻 |

一个「安静的变形」比一个错误糟得多：它让一条被改过的参数看起来像是模型本来就这么说的，
让一条被清空的观测看起来像是工具没返回东西。**静默地丢材料，正是这个系统最不能容忍的
一类错误**——证据链的价值全在「它没撒谎」这一条上。

于是参数进门（`invalid_args`）和结果出门（`invalid_result`）用的是同一个函数。
这条边界因此有一个说得清的含义：**过了这道边界的东西，都是日志装得下的东西。** 步 7
的 JSONL 是它的直接受益者。*（步 7 的追加：受益是真的，但也漏了一个洞——`decision_made`
里带着模型给的 `ToolIntent.args`，它在**工具开跑之前**就已经落日志了，那时这道关还没经过。
所以步 7 在日志那一侧补了同一判据的最后一道关：序列化之后再读回来比一次，不相等就拒写
（`docs/07-durability-replay.md` 边界决定 3）。两个对象、两个时机，判据是同一条。）*

代价是一条今天读起来可能显得严的规则：工具返回 `value: undefined` 会被拒绝，工具必须
显式写 `null`。这是对的——步 2 已经定过「用 `| null` 而不是 `?`」，`undefined` 在 JS 里
是「没写」，而「这条材料没有内容」应该是一个确定的事实。

### 5. 被预算拦下的调用与一次失败的调用是两件事

这两条路径看起来很像（都「没拿到材料」），但在事件流里的表现**必须不同**，而且有一条
测试钉着这个差别：

| | 预算拦下（步 5） | 执行层拒绝（本步） |
|---|---|---|
| 谁干的 | 我们（Runtime 的账本） | 执行层（检查） |
| 调用到过端口吗 | **没有** | 到了（被拒的是参数/名字，不是调用本身） |
| 事件 | 只有 `decision_made` | `tool_started` + `tool_completed{error}` |
| 消耗一次工具预算 | 否 | **是** |
| Run 的结局 | `run_failed{budget_tools}` | 继续，最后 `partial` |

步 5 为「超限那次不该在日志里留下一条 `tool_started`」专门改过一次实现（`tool_started`
曾经说过谎）。这里的方向相反但是同一条原则：**事件流必须说真话，而真话取决于这一次
调用到底走到了哪一步。** 预算拒绝是我们没让它出发；参数不合法是它出发了、被门口拦回来。
后者确实消耗了一次预算，因为预算保护的是「模型要求发起多少次调用」这件事。

### 6. 截断是**替换**，不是省略

超过 `OBSERVATION_CHAR_LIMIT`（8000 字符）的结果，`value` 会变成一段文本预览，
并置上 `truncated: true`。

不保留原类型是刻意的：砍掉一半的 JSON 已经不是一个对象了，假装它还是，只会让下游拿到
一个解析不了的「对象」。所以 `truncated: true` 的准确含义是：**`value` 是一段预览，
不是原始值**。看到它的人立刻知道两件事——手上不是完整材料，而且它不能被当成完整材料
解析。

上限是常量、**故意不做成配置项**（与 `CALL_TIMEOUT_MS` 一样）。没有证据表明它需要按
调用方变化，而多一个旋钮就多一种「同一个任务在不同配置下产出了不同证据」的可能——
那正是回放最怕的事。它守住的也不是「大文件不好」，而是两条更硬的事实：日志必须有界
（一次读 20 个文件的 Run 不该写出一份几十 MB 的证据），以及**截断必须可见**。

### 7. `provenance` 只能由我们写：两道守卫，缺一不可

步 2 用一行编译期证明说「工具声明不了 `provenance` / `truncated`」，这一步从运行时再确认
一次，而**破坏性验证暴露了它是两道独立的防线**：

1. `normalizeOutcome` **重建**返回对象，只取 `value` 与 `error` 两个键。工具多塞的键
   到不了组装点；
2. `assembleObservation` **构造**新的观测对象，而不是复制 `ToolOutcome`。

只拆掉第一道时，第二道仍然拦得住（所以那条测试不会响）；两道都拆掉时，测试里那条
「工具试图注入 provenance」当场失败，观测的来源变成了 `工具自己编的来源`。
**一条被伪造的 `provenance` 比没有 provenance 糟得多**：它让一条编造的材料看起来可追溯，
而那正是整条追溯链要防的事。

### 8. `missingMaterial` 的读侧与写侧住在同一个文件里

`collectMissingMaterial(state)` 是执行层的读侧，它与那些错误码住在同一个文件里不是巧合：
**「什么算失败」（写侧）与「什么算缺失」（读侧）必须是同一套判断**，分开放就一定会有
一次它们悄悄不一致。清单有三条来源，都从 `transcript` 派生（状态里没有第二份投影，
步 2）：

1. 观测带 `error` ——工具失败了；
2. 观测 `truncated` ——拿到了，但只拿到一部分；
3. 有 `call_tool` 的意图、后面没有对应的观测 ——调用没有回来。

第 3 条今天从 `run_completed` 这条路径上是够不着的（调用一旦被停止信号打断，这次 Run
就不会走到 `run_completed`），但它是状态的合法形状，而回放（步 7）会从任意前缀重建
状态——那时它就会出现。所以它在这里，不因为「现在不会发生」而省略。

*（步 7 的追加：**这条预测被证伪了。** 回放确实能重建任意前缀，但它**照抄实时语义**：
`reduce` 只在观测到位时被调用一次，所以 `transcript` 里永远不会出现「assistant 的
`call_tool` 没有配对消息」这个形状——回放一个停在「意图已下、观测未回」的前缀，得到的
状态里没有那条意图，第 3 条来源仍然够不着（`test/replay-idempotence.test.ts` 有一条测试
把这件事钉住）。要改它，得先有恢复语义：一次崩溃在调用中途的 Run，恢复之后「那条在途的
调用」该以什么形状回到状态里。上面这段不修改——它是这一步当时的事实。）*

清单项的形状是 `工具名(参数摘要)：原因`，不是光秃秃的工具名：缺失的粒度不是
「`read_file` 这个工具没了」，而是「这一次 `read_file` 没读回来」。同一条重复出现只记
一次——同一个工具用同样的参数失败三次，是同一份材料缺了三次，不是三份材料。

### 被实现抓到的一个缺陷：一次失败的 Run 被报成了 `complete`

写这个文件时，`toolDeps()` 只交出了「写侧」的两半（`tools` + `assembleObservation`）。
测试立刻给出 5 条失败：

```text
expected 'complete' to be 'partial'
```

失败被完整地记录进了观测、也进了事件流，**然后被安静地忽略**——因为 `collectMissingMaterial`
还是 `createRuntime` 的默认实现 `() => []`。终态于是宣称这次 Run 完整地完成了任务，
而它的证据里躺着一句 `tool_failed`。这类 bug 不会报错、不会崩、只会让结论比证据更自信，
是这个项目最该防的一类。

修法不是「记得传第三个字段」，而是**让三件一起交付**：`toolDeps()` 现在交出三个字段，
形状由 `Required<Pick<RunAgentOptions, …>>` 钉住。第一次写的时候用的是不带 `Required`
的 `Pick`，它是**没有牙的**——`RunAgentOptions` 里这三个字段都是可选的，`Pick` 会保留
可选性，漏掉一个照样编译通过。加上 `Required` 之后，漏掉第三个是 `TS2741`。

这件事的教训值得单独记一笔：**「接线」这种错误，靠纪律是防不住的，只有让它编译不过。**

## 三、验证

```bash
npm run typecheck
npm test
```

`test/tool-runner.test.ts`（18 条）覆盖：

1. **名字与参数**——allowlist 之外的名字被拒**且端口一次都没被碰到**、参数不是对象被拒、
   含 `undefined` / 函数 / `NaN` 的参数被拒且消息点得出 `args.lines[1]` 这样的路径、
   循环引用被拒（而不是让序列化在写日志那一刻爆）、合法的嵌套参数照常通过；
2. **返回值**——`new Map()` 被拒（`invalid_result`）且被拒的值不进状态、工具抛异常落成
   `tool_failed` 且 Run 照样走完（**没有 `run_failed`**）、执行层交回非 `ToolOutcome`
   被拒、错误字段形状不对被拒；
3. **超时与取消的分野**——单次调用超时是 `timeout` 观测且 Run 继续
   （`run_failed` 一条都没有）、Run 被取消时在途调用**不会**变成 timeout 观测而是
   `run_cancelled`（`typesOf` 逐条断言）、调用前已中止则直接抛出且一次都不往下走；
4. **截断**——超长结果的 `value` 变成预览、`truncated` 为真、**原文的尾部在整份日志里
   找不到**、截断使终态变成 `partial` 并在清单里点名；短结果不截断；
5. **provenance**——工具试图注入 `provenance` / `truncated` 无效，观测里是**我们**写的
   那一份（`at` 由注入的确定性时钟钉死，证明它不来自某处偷偷读的 `Date.now()`），
   且观测**恰好**是 `error / provenance / tool / truncated / value` 五个键；
6. **missingMaterial**——三条来源都算、重复只记一次、成功的观测不进清单；
   一次都没出错的 Run 清单为空且终态 `complete`；
7. **接线**——`toolDeps()` 恰好交出那三个字段，且与 `runner.tools` / `runner.assembleObservation`
   是同一个对象（运行时的这一条与 `Required<Pick<…>>` 的编译期证明是同一条主张的两面）。

有两类断言不能省：`h.tools.calls` 的**计数**（被拒绝的调用一次都不该到达执行层——
只看观测的话，一个「先调用再说不合法」的执行层看起来完全正确，但副作用已经发生了），
以及**整份日志里搜原文尾部**（只看观测的话，一个「状态里截断了但仍然把它写进日志」的
实现看起来也对）。

`test/no-runtime-deps.test.ts` 未改：`src/runtime` 仍然没有一行 Node 内置模块或 SDK
import（`AbortSignal.any` / `AbortSignal.timeout` 都是全局）。步 8 会把
「core 与 runtime 零 SDK import」写成断言。

全量：`112 passed / 6 files`（步 5 是 94），`typecheck` 0 error。

**破坏性验证**（改动已还原）——五条守卫都必须会响，不然它只是装饰：

| 人为破坏 | 结果 |
|---|---|
| 拆掉名字与参数检查 | 4 条当场失败；其中第一条是靠**端口调用计数**抓到的（观测仍然「对」，调用真的下去了） |
| 拆掉截断 | 「原文的尾部不在日志里」当场失败 |
| 让归因退回「看谁抛的」 | 取消那条当场失败（取消被误报成工具超时，Run 变成 `partial` 而不是 `cancelled`） |
| 拆掉 `normalizeOutcome` 的重建 + 让组装点相信工具自报的来源 | 「工具试图注入 provenance」当场失败（观测来源变成`工具自己编的来源`） |
| `toolDeps()` 漏掉读侧 | 5 条测试失败（失败被报成 `complete`）；补上 `Required<…>` 之后变成 `TS2741` 编译错误 |

## 四、刻意推迟的东西

| 推迟的 | 推迟到 | 理由 |
|---|---|---|
| 每个工具自己的参数 **schema** 校验（「`read_file` 需要一个字符串 `path`」） | step 8 | 它需要知道每个工具的 schema，而 schema 是适配器的词汇（工具描述住在那里）。本步只做**形状**校验——那是执行层在不认识任何工具的前提下唯一能做的检查，也是**唯一能对所有工具成立**的检查。 |
| 真正执行工具的适配器（读写文件、跑命令） | step 8 | 本步只有假工具。执行层是**包装**，不替工具干活。 |
| `provenance.source` 细到材料本身（`read_file` 读的是哪个文件） | step 8 / 由 `Evidence` 承担 | 要细到文件路径，就得让工具声明「我从哪读的」——而那正是步 2 禁止工具自填的字段。所以它要么由适配器在 `ToolOutcome` 之外补（那是 step 8 的决定），要么由 `Evidence` 回答（论断指向文件行号才是最终答案，步 2）。 |
| 截断上限与单次超时做成配置项 | 未定 | 见边界决定 6：没有证据表明它们需要按调用方变化。 |
| 重试（`maxRetries` 已在词汇里） | step 8 | 要有「这个错误值不值得重试」的判断，而那需要 provider 的错误分类。 |
| token 预算的执法 | step 8 | 同 `docs/05`：没有 usage 来源，也没有对应的失败码。 |

## 五、局限（如实记录）

1. **只有假通道。** 与本步对照的是脚本化的工具桩。真实的文件系统错误、编码问题、
   超大文件、命令执行的副作用一概还没遇到（步 8）。「失败被隔离」这件事本步证明的是
   **结构**，不是「真实工具出错时我们一定接得住」。
2. **`provenance.source` 的粒度是工具名，不是材料。** 观测说得清「这条是 `read_file`
   取回来的」，说不清「它读的是哪个文件」。理由见上表。
3. **`truncated` 在 `tool_completed` 事件上没有字段。** 事件词汇（步 2）里没有它，
   而本步不擅自加字段——加一个字段是所有日志读者都要跟着变的事。要看到它得看紧跟其后
   的 `observation_added`。这是一个真实的可用性缺口，记在这里而不是悄悄绕过。
4. **单次调用超时被隔离，所以 `run_failed{timeout}` 今天不可能来自工具侧。**
   它要等步 8 的模型请求超时才有一个致命的产生者。
5. **`missingMaterial` 的第 3 条来源（有意图、无观测）在 `run_completed` 路径上不可达。**
   它是为回放准备的，今天只有直接调用 `collectMissingMaterial` 的单元测试能走到它。
   *（步 7 的追加：回放也走不到它——见上面边界决定 8 后面的追加。它仍然只有手工构造
   状态才够得着。）*
6. **`CALL_TIMEOUT_MS` 的后果是「这条材料没拿到」，不是「再等等」。** 没有中间状态：
   超时即结束这一次调用，不能续。重试是步 8 的事。
7. **超时定时器无法取消**，只能等它到点（`AbortSignal.timeout` 的定时器是 unref 的，
   不拖住进程）。这是步 5 那笔账的延续：每一次工具调用都会留下一个到点空转的定时器。
